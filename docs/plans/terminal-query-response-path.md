# Terminal query response path

## Status

In progress. The core query-response path (design steps 1–4) is **implemented**:
the Ghostty wrapper now answers DSR/DA/DECRQM/size/XTVERSION/kitty-keyboard
queries via a new `on_pty_response` FFI callback →
`EventSink::on_pty_response` → `ControlEvent::PtyResponse`, and both the
in-process daemon and the isolated worker drain those replies to the pane's
`PtyWriter` (serialised with user input). The `kmux-ghostty` C ABI is bumped
**5 → 6**. Verified end to end in `crates/kmuxd/tests/query_response_e2e.rs`
under both engines.

Two deliberate simplifications vs. the original design below:

- `ControlEvent::PtyResponse` carries **borrowed** bytes (`&[u8]`), not an owned
  `Vec<u8>` — consistent with the rest of the catalog; the consumer copies into
  an owned buffer before enqueuing, which is what actually satisfies the
  asynchronous-delivery requirement.
- The isolated worker writes its **own** replies (it owns the PTY write half), so
  no worker-protocol frame or version bump is needed (design step 4 assumed the
  daemon owns the write path in the isolated engine; it does not).

**Remaining:** design step 5 (synchronized output, DEC 2026) is still open and
is intentionally tracked as a separate change so query-response correctness can
be tested independently.

## Problem report

Some full-screen and interactive terminal programs appear to stop repainting
until either a short timeout expires or the user supplies another keypress.
Two recurring examples are:

- After exiting Vim with `:q`, restoring and repainting the main shell is
  perceptibly delayed.
- During Bash path completion backed by `fzf`, the fzf TUI may remain invisible
  until the user starts typing.

The problem has survived changes of terminal backend, including the former
Alacritty-based implementation. That points to a shared architectural boundary
rather than backend-specific cell rendering.

## Root cause

The server-authoritative VT path is one-way for terminal control traffic:

```text
child process -> PTY output -> VT parser -> terminal model -> grid diff -> client
```

It has no corresponding route for replies generated by the terminal emulator:

```text
child process <- PTY input <- terminal query response <- VT parser
```

The Ghostty wrapper delegates most actions to `gvt.ReadonlyHandler`. That
handler deliberately ignores actions without terminal-model side effects,
including queries that require a response:

- device status and cursor position reports (DSR, including `CSI 5n` and
  `CSI 6n`);
- primary and secondary device attributes (DA1/DA2);
- terminal size reports;
- DECRQM mode queries;
- XTVERSION;
- kitty keyboard protocol queries; and
- enquiry/answerback requests.

`kmux_ghostty_feed` returns only a success/error status, so it cannot return
generated response bytes. The Rust event sink only models externally visible
side effects such as titles, clipboard writes, progress, and hyperlinks. No
event variant carries bytes that must be written back to the child PTY.

This behavior is explicitly documented and tested today: color queries and all
other DA/DSR-style queries are parsed but intentionally not answered. That
boundary is unsuitable for a general terminal emulator. Programs commonly
wait for these replies before completing initialization, teardown, or layout.
A timeout explains the delayed Vim shell restoration, while another input event
advancing fzf's event loop explains why typing can make its first frame appear.

The ordinary display path does not show the same defect. `session_diff_loop`
feeds every PTY read into the emulator, drains immediately available output,
computes a diff, and broadcasts it without a deliberate delay. Existing
alternate-screen and fzf diff tests also show that supported state mutations do
produce cell diffs. The missing bidirectional reply path is therefore the
primary root cause, not a renderer invalidation failure.

## Relevant code

- `crates/kmux-ghostty-sys/zig/src/wrapper.zig`: `Handler.vt` delegates query
  actions to `ReadonlyHandler`; `kmux_ghostty_feed` has no response-byte output.
- `vendor/ghostty/src/terminal/stream_readonly.zig`: explicitly drops
  `request_mode`, `size_report`, `xtversion`, `device_attributes`,
  `device_status`, and `kitty_keyboard_query`.
- `crates/kmux-ghostty/src/lib.rs`: safe `GhosttyTerm::feed` exposes only
  success or failure.
- `crates/kmux-vt-core/src/backend/control_event.rs`: the shared event catalog
  has no terminal-response variant.
- `crates/kmux-vt-core/src/backend/ghostty/mod.rs`: tests and comments currently
  codify ignored query behavior.
- `crates/kmuxd/src/relay.rs`: owns the in-process PTY read/diff loop but has no
  response channel to its corresponding writer.
- `crates/kmux-vt-worker/src/main.rs` and `kmux-worker-protocol`: the isolated
  backend needs the same response facility across the worker boundary.
- `docs/terminal-backend.md`: describes ignored queries as an intentional
  limitation and must be corrected with the implementation.

## Proposed design

### 1. Represent terminal-generated replies

Add an owned terminal-response event at the backend boundary. It should carry
the exact byte sequence that must be delivered to the child process, for
example:

```rust
ControlEvent::PtyResponse(Vec<u8>)
```

Borrowed data is inappropriate because delivery must be asynchronous and may
outlive the parser callback. If response traffic is frequent enough to warrant
separation from UI-facing control events, introduce a dedicated response sink;
either design must preserve a single auditable route for all VT queries.

### 2. Generate correct replies in the Ghostty wrapper

Intercept query actions before delegating to `ReadonlyHandler`, derive replies
from the live terminal state, and emit them through the response callback.
Initial coverage should include:

1. DSR status and cursor position.
2. DA1 and DA2 with a stable kmux capability identity.
3. `CSI t` character and pixel size reports using `BackendSize`.
4. DECRQM replies based on the terminal's current mode state.
5. XTVERSION.
6. Kitty keyboard protocol queries.
7. ENQ if kmux chooses to advertise an answerback string.

Response formatting should reuse Ghostty's protocol types or formatter helpers
where practical. Capability claims must be conservative: kmux must not
advertise features that are not implemented end to end.

### 3. Write replies without blocking the parser

The VT event-sink contract is synchronous and non-blocking. A parser callback
must therefore enqueue owned response bytes and return immediately. A separate
daemon task should drain that queue into the pane's existing `PtyWriter`.

Ordering requirements:

- replies from one pane remain FIFO;
- query replies are not interleaved within a single encoded response;
- response writes use the same serialization point as user input so concurrent
  keypress and reply writes cannot corrupt one another; and
- a closed pane drops pending replies without blocking shutdown.

Do not write to the PTY while holding the terminal-state mutex or from inside
`GhosttyTerm::feed`; doing so risks parser reentrancy and lock-order deadlocks.

### 4. Support process-isolated VT workers

Add a versioned worker event for response bytes. The worker parses the query and
sends the response event to the daemon; the daemon remains responsible for the
actual PTY write. This keeps PTY ownership and input serialization consistent
between in-process and isolated engines.

Changing the worker message contract requires the corresponding worker protocol
version bump and mismatch tests, per the repository correctness rules.

### 5. Correct synchronized-output handling separately

DEC private mode 2026 (`synchronized_output`) is also ignored by the readonly
handler. This is not the best explanation for applications blocking, but it can
cause partial or torn frames.

Track synchronized-output state and suppress intermediate broadcasts while the
mode is active, then compute and broadcast the accumulated final diff when it
is reset. Add a bounded failsafe so a malformed or terminated application
cannot suppress rendering forever. Treat this as a distinct implementation
step so query-response correctness can be tested independently.

## Verification plan

### Backend unit tests

- Feed `CSI 5n` and assert an immediate `CSI 0n` response.
- Place the cursor at a known location, feed `CSI 6n`, and assert the correct
  one-based cursor-position response.
- Verify DA1/DA2, size, DECRQM, XTVERSION, and kitty keyboard replies.
- Split every query across multiple `feed` calls to exercise parser chunking.
- Feed multiple queries in one chunk and verify FIFO response ordering.
- Confirm ordinary output following a query still produces the expected grid
  diff.

### Daemon/PTY integration tests

- Spawn a child that emits `CSI 6n`, reads stdin with a short deadline, and
  reports the received bytes; prove the response completes without timeout.
- Exercise the same test under both in-process and process-isolated session
  engines.
- Interleave a user key event with a terminal query and verify each complete
  byte sequence reaches the child without corruption.
- Close a pane with queued replies and verify clean shutdown.

### Reproduction regressions

- Capture the relevant Vim exit byte stream and verify the shell-restoration
  exchange completes without waiting for a timeout.
- Capture the fzf Bash-completion startup exchange and verify its first visible
  frame is broadcast without requiring another keypress.
- Run both cases on the default macOS frontend and GTK frontend; the behavior
  should be frontend-independent because the fix lives at the daemon/PTY
  boundary.
- Record timing around query receipt, response enqueue, PTY write, subsequent
  output, diff broadcast, client apply, and paint. This distinguishes protocol
  stalls from any remaining render scheduling latency.

### Synchronized-output regressions

- Feed a multi-part frame inside `DECSET 2026` / `DECRST 2026`; assert no
  intermediate client diff and one final accumulated diff.
- Verify the failsafe releases a frame if the program never resets the mode.
- Verify alternate-screen enter/exit inside a synchronized update restores the
  correct main-screen contents.

## Completion criteria

- Supported terminal queries receive standards-compatible replies without
  waiting for user input or a timeout.
- In-process and isolated backends behave identically.
- Vim `:q` restores the shell promptly and fzf completion paints its initial TUI
  without an extra keypress.
- Query responses cannot block the parser, reorder within a pane, or deadlock
  against input and terminal-state locks.
- Documentation no longer describes dropping all terminal queries as an
  acceptable architectural boundary.
- Existing grid conformance, workspace tests, Clippy, formatting checks, and
  both GPU and no-GPU builds pass.

## Risks and decisions requiring care

- Device-attribute replies are compatibility promises. Advertise only stable,
  implemented capabilities.
- Cursor reports are one-based and may be affected by origin mode; tests must
  cover both normal and origin-relative coordinates.
- Some replies depend on pixel dimensions, which may be unknown (`0`). Define a
  conservative response or non-response policy for unknown values.
- Terminal responses and user input share the PTY input direction. Their
  serialization mechanism must preserve complete messages without imposing a
  blocking lock inside the parser.
- Worker protocol changes are versioned and must refuse mismatches.

## Non-goals

- Moving VT parsing into GUI clients.
- Replacing Ghostty's terminal model.
- Treating a forced redraw as a substitute for terminal protocol replies.
- Advertising every extension supported by Ghostty before kmux supports it end
  to end.
